03

The Specification as Contract

Published18 min read·rev a91f3c2

§ 3.1What makes a specification a contract

A description becomes a contract when something downstream can be held to it. Prose descriptions cannot do this. They accommodate.

A specification is a contract when three things are true. It is committed before the work starts. It is the sole authority when the code and the description disagree. And the tests are derived from it rather than from the implementation.

Committed before the work starts

If the spec is not in version control before generation, you have no contract. You have a chat log.1

Rail and utility heading

Map .t-display book title. Cover only. Once per site.
.t-numeral chapter number. Decorative weight, colour --line. Never a link.
h1 chapter title. One per page.
h2 section. Carries .sec-mark above it in accent mono.
h3 subsection. No marker.
h4 utility label only. Mono, uppercase, --ink-3. Not part of the reading hierarchy.
Spacing h2 margin-top --sp-6 · h3 --sp-5 · p bottom --sp-3

Prose elements

Everything inside .prose. The measure is applied by the container, never by the element.

Body text at seventeen pixels over a sixty-eight character measure. Strong sits at weight 600 and lifts to --ink. Italic drops to --ink-2. Inline code such as specs/014-rate-limit/spec.md takes a hairline border and the sunken background.

Unordered list · marker is a 9px accent rule

  • Limit is applied per tenant id, not per IP
  • On rejection, return 429 with Retry-After in whole seconds
  • The counter is shared across all instances

Ordered list · leading zero, mono

  1. Commit the specification
  2. Run the builder against the committed file
  3. Derive tests from behaviour statements
Generation stopped being the constraint. Specification became the constraint.
An out of date specification is not documentation debt. It is a false statement about the system. Chapter 03 · The Specification as Contract
Containers .prose sets max-width:var(--measure). Nothing else sets a measure.
Lists ul marker: 9×1px --accent rule at top .72em. No discs, ever.
ol counter: decimal-leading-zero, mono, --ink-3.
Rules .rule full width · .rule--soft separators · .rule--accent 48px accent stub
Quotes blockquote and .quote are the same treatment. Display face, 21px, 2px accent left edge. cite is optional.

13

Rules for implementation

The constraints that keep generated output on-theme. These are the statements to put in the specification, not this prose.

Do
  • Reference semantic tokens only. A component never names a Nord value
  • Use the twelve type steps as given. No intermediate sizes
  • Express structure with hairlines and background shifts
  • Put every uppercase label in the mono face with tracking opened
  • Keep one primary button per view, and one gauge per page
  • Use state colour only where it encodes state
  • Set spacing from the scale, never from an arbitrary pixel value
Do not
  • Add border radius. The system is square, everywhere, deliberately
  • Add shadows, gradients, glows or glass effects
  • Introduce a new accent colour or a fourth status
  • Set uppercase in the display or body face
  • Use a dashed border anywhere except the empty state
  • Put icons in callouts. The label does that job
  • Let a reading column exceed --measure
  • Animate anything on entry. Motion responds to input only
  1. Footnote reference and list, shown here so the pattern is documented. Reference is mono, accent, superscript. The list rule is a full hairline above.
